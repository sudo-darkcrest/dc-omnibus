Cloud, Virtualization, Containers and Storage

Why this matters. Almost every workload today runs on a hypervisor, in a container, in someone's cloud, or all three, and every one of them stores data somewhere. These ideas show up in A+ (virtualization and cloud), Network+ (cloud networking), Security+ (architecture models and shared responsibility) and data center work (storage, density, power for virtualized hosts). This module connects them so you can tell which layer you own and which one you rent.

You will be able to

  • Explain Type 1 vs Type 2 hypervisors, overcommit, live migration and HA (High Availability) clusters.
  • Compare containers and VMs (Virtual Machine), and describe Kubernetes, serverless, microservices, IaC and CI/CD (Continuous Integration / Continuous Delivery).
  • Choose cloud service and deployment models and say who secures what under shared responsibility.
  • Design basic cloud networks with VPCs (Virtual Private Cloud), subnets, security groups, NACLs (Network Access Control List) and gateways.
  • Pick DAS (Direct-Attached Storage), NAS (Network Attached Storage) or SAN (Storage Area Network) and block, file or object storage, and reason about replication and RPO (Recovery Point Objective).

1. Virtualization in depth

Type 1 (bare metal)

The hypervisor runs directly on hardware: VMware ESXi, Microsoft Hyper-V, KVM (Keyboard, Video, Mouse), Xen. Used in data centers and clouds. Less overhead, stronger isolation.

Type 2 (hosted)

Runs as an app on a normal OS (Operating System): VirtualBox, VMware Workstation, Parallels. Good for labs and desktops.

  • vCPU (Virtual Central Processing Unit): a virtual processor scheduled onto physical cores/threads. Overcommit means assigning more vCPUs (or RAM (Random Access Memory)) than physically exist, betting not all VMs peak at once. A common starting vCPU:pCPU ratio is about 3:1 to 4:1 for general workloads; databases get less. Too much overcommit shows up as CPU (Central Processing Unit) ready time and memory ballooning/swapping.
  • Live migration (vMotion, Hyper-V Live Migration) moves a running VM between hosts with no downtime, needing shared or replicated storage and fast networking.
  • HA cluster: if a host fails, its VMs restart on surviving hosts (a short outage). Fault tolerance runs a shadow copy in lockstep for zero downtime. DRS (Distributed Resource Scheduler)-style balancing moves VMs to even out load.
  • Virtual switches connect VMs to each other and to physical uplinks, supporting VLAN (Virtual Local Area Network) tagging, NIC (Network Interface Card) teaming and port groups. Distributed virtual switches span many hosts.
  • Snapshots capture a VM's state for quick rollback; they are not backups (they depend on the base disk and slow things down if kept long).
  • Security: VM escape, VM sprawl (unmanaged VMs) and resource reuse are the risks; patch hypervisors and keep an inventory.
A hypervisor is an apartment building manager: one building (server), many apartments (VMs) each with its own front door and kitchen (OS). Containers are rooms in a shared house: everyone has a private room but shares the kitchen (kernel).

"Containers are as isolated as VMs." No: containers share the host kernel, so a kernel exploit can affect all of them. High-security multi-tenant workloads often run containers inside VMs.

3. Cloud models and shared responsibility

NIST (National Institute of Standards and Technology) SP (Special Publication) 800-145 defines cloud by five characteristics: on-demand self-service, broad network access, resource pooling (multitenancy), rapid elasticity and measured service.

Service models

  • IaaS (Infrastructure as a Service): rent VMs, storage and networks; you manage OS and up (e.g., EC2 (Elastic Compute Cloud), Azure VMs).
  • PaaS (Platform as a Service): a managed platform; you deploy code and data (e.g., App Service, managed databases).
  • SaaS (Software as a Service): finished software (e.g., Microsoft 365, Salesforce).
  • FaaS: serverless functions (e.g., Lambda, Azure Functions).

Deployment models

  • Public: shared provider infrastructure.
  • Private: dedicated to one organization (on-prem or hosted).
  • Hybrid: public plus private, connected and orchestrated.
  • Community: shared by organizations with common needs (e.g., government).
  • Multi-cloud: more than one public provider, for resilience or best-of-breed.
  • Regions are geographic areas; availability zones are separate data centers (independent power, cooling, networking) within a region. Spread across AZs for high availability, across regions for disaster recovery.
  • Scalability: the ability to grow (vertical = bigger instance, horizontal = more instances). Elasticity: growing and shrinking automatically with demand.
  • Cost basics: pay-as-you-go (OpEx) vs buying hardware (CapEx); reserved/committed-use discounts; spot instances; egress (data out) charges; tagging for cost allocation; turn off idle resources.
Shared responsibility: the provider is always responsible for the physical data center; the customer is always responsible for their data, identities and access, and (in most models) how they configure the service. Everything in between shifts toward the provider from IaaS to PaaS to SaaS. Lab 1 shows it layer by layer.

5. Cloud security

  • IAM (Identity and Access Management): least-privilege roles and policies, MFA for all humans, no long-lived access keys where avoidable, separate accounts/subscriptions for environments.
  • CASB (cloud access security broker): visibility and policy enforcement between users and SaaS apps (shadow IT (Information Technology) discovery, DLP (Data Loss Prevention), access control).
  • CSPM (cloud security posture management): continuously scans cloud configurations for misconfigurations against benchmarks.
  • Misconfiguration is the top cloud risk: public storage buckets, open security groups (0.0.0.0/0 on SSH/RDP), overly permissive IAM, disabled logging, unencrypted snapshots.
  • Encryption and key management: encryption at rest and in transit; provider-managed keys vs customer-managed keys (KMS) vs bring/hold your own key (HSM).
  • Logging: enable control-plane audit logs (who changed what) and flow logs; send them to a SIEM (Security Information and Event Management).

Block

Raw volumes the OS formats; lowest latency; databases and VM disks. Cloud: EBS (Elastic Block Store), Azure Managed Disks.

File

Hierarchical folders over SMB/NFS; shared access with permissions. Cloud: EFS (Encrypting File System), Azure Files.

Object

Flat namespace of objects with metadata, accessed by HTTP (HyperText Transfer Protocol) API; massive scale, cheap; backups, media, data lakes, static websites. Cloud: S3, Azure Blob.

7. Moving a workload to the cloud

Companies rarely build in the cloud from nothing. They move existing applications. The common strategies are often called the "R's of migration".

StrategyWhat it meansExample
Rehost ("lift and shift")Move virtual machines as they areCopy the accounting server VM into cloud compute
ReplatformSmall changes to use managed servicesMove the database to a managed database service
RefactorRebuild for cloud-native designSplit a big app into containers or serverless functions
RepurchaseReplace with a SaaS productSwap an in-house email server for a hosted email service
RetainKeep on-premises for nowA system tied to factory hardware
RetireSwitch offAn old app nobody uses

A sensible order of work

  1. Inventory applications and their dependencies (what talks to what).
  2. Set up the landing zone: accounts, networking, identity, logging and guardrails.
  3. Move a low-risk app first to learn.
  4. Test performance, backups and failover in the cloud before cut-over.
  5. Watch costs closely for the first few months; right-size anything oversized.
"Lift and shift" is fast but often costs more than expected, because servers sized for peak load on-premises keep running at full size 24 hours a day in the cloud.

8. From code to container: a simple walkthrough

Containers can feel abstract. Here is the life of one small web app.

  1. Write a Dockerfile: a short recipe that starts from a base image (for example a slim Linux with Python), copies the app in, installs its libraries and says which command starts it.
  2. Build an image: the recipe produces a read-only image, a few hundred megabytes, containing the app and everything it needs.
  3. Scan it: a scanner checks the image for known vulnerable libraries before it is used.
  4. Push to a registry: the image is stored in a container registry with a version tag.
  5. Run it: a container runtime starts the image as an isolated process sharing the host's kernel. It starts in seconds.
  6. Orchestrate: Kubernetes runs several copies across many servers, restarts any that crash, and spreads traffic across them.
  7. Update: to release a new version, build a new image and roll it out gradually; roll back if errors rise.
An image is a recipe card that has already been cooked and frozen into a ready meal. A container is that meal heated up and served. You can heat up as many identical meals as you need.
